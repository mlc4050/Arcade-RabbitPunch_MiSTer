# Sprite row pipeline

`rabbitpunch_sprite_row.vhd` wraps the unchanged JTFRAME drawer for one row of
a native 16x32 Rabbit Punch sprite. New logic is VHDL with unsigned ports.
The reference is MAME 0.289 `src/mame/vsystem/rpunch.cpp`, `splayout` and
`draw_sprites`, pinned in HARDWARE_NOTES.md.

The producer waits for `o_row_ready`, supplies sprite code, local row, destination
X/Y, palette, flips and the behind-foreground tag, then asserts `i_row_valid`
for the accepting edge. Metadata is latched. The adapter pulses the drawer's
start input and issues one external ROM request at a time. Its request is a
single-cycle pulse; a future shared transport must retain it until serviced.
There is no ROM response backpressure, and every accepted request must receive
exactly one response even if the adapter is reset.

The donor draws 16-high cells, so the adapter appends the vertically adjusted
fifth row bit to the 11-bit sprite code. It maps donor `{code12,half,row4}`
addresses into packed-ROM `{code11,row5,half}` word addresses. ROM words are
little-endian: the lowest-address byte is in bits 7..0. MAME's sprite layout
reverses byte pairs within each group of four pixels; the adapter converts
those packed pixels into the four bitplanes consumed by JTFRAME.

The second eight-pixel ROM word is requested while the first half is drawing.
Outputs comprise two eight-pixel bursts with a possible wait between them.
There is no output backpressure; the consumer must accept each asserted pixel.
Coordinates wrap at 512. Palette indices cover 768..1023, pen 15 is transparent,
and the priority tag accompanies every pixel. This adapter does not decide which
sprite wins an overlap or whether a foreground tile hides a sprite.

Reset suppresses output immediately, drops the partial row and drains any
outstanding ROM reply before accepting a fresh row. There is no line RAM or
frame RAM in this row adapter. Physical raster, original-board descriptor
latching and shared SDRAM arbitration remain open. Scanline selection and
sprite line storage are described below and in VIDEO_PRIORITY.md.
In particular, a successful row test does not prove a whole scanline deadline.

## Verification

`sim/video/sprite_row_tb.vhd` drives rows generated by `run_sprite_tests.py`.
The bench supplies graphics ROM data and checks every emitted pixel against
an independent direct sampler of the MAME layout. It verifies both ROM word
addresses, exactly two requests and sixteen pixels per completed row, and
that the second request occurs before all first-half pixels have been emitted.

The synthetic set checks 30720 rows / 491520 pixels: five code boundaries,
all 32 rows, all sixteen palette groups, both flip directions independently,
0/3/11 additional ROM wait cycles, X wrapping and changing inputs while busy.
Fresh rows after resets are checked separately. Reset cases interrupt the
first ROM wait, active drawing, the second ROM wait and the pre-request phase.

Each of the six real MAME fixtures supplies all 54 active descriptors and all
32 local rows: 1728 rows / 27648 pixels per scene, 165888 pixels total.
These exercise graphics, metadata and row addressing; they do not yet compare
sprite overlap, visible clipping or complete mixed frames. Commands come from
captured descriptors, while expected pens are sampled directly from ROM bytes.
No ROM data is committed. Hashes and results are in reference/sprite_checks.json.

```powershell
./scripts/d_drive.ps1 scripts/run_sprite_tests.py
./scripts/d_drive.ps1 scripts/build_staged.py --synth-check sprites
```

The standalone Quartus project tests only this adapter and its JTFRAME drawer
at the 48 MHz evaluation clock, with virtual I/O. This is not a full-core fit,
a final board clock choice or a deployable RBF.

Commit 2f886cb passes that Quartus 17.0.2 fit on 5CSEBA6U23I7: 116 ALMs,
170 registers, zero M10K and zero DSP blocks. All corners pass setup, hold
and minimum pulse width; worst setup slack is +10.788 ns and worst hold
slack is +0.146 ns, with zero illegal clocks or unconstrained paths.
The adapter and donor hierarchy survive synthesis. See reference/sprites_synth.json.

## Scanline selection

`rabbitpunch_sprite_scan.vhd` accepts logical Y, count, priority and video flags,
and scans descriptors in descending index order as MAME does. Count zero completes
without reading RAM. Every entry first fetches Y; intersecting entries then fetch
attributes and X. Row eligibility is `(line_y + sprite_y - 1) mod 512 < 32`.
The emitted row carries unflipped local Y, code, wrapped X+8, palette/flips,
descriptor index and the behind-foreground tag. The row drawer applies the flips.

One decoded candidate may wait for the drawer while its current row completes.
All candidate fields remain stable under backpressure. Reset discards a queued
candidate and drains any accepted descriptor reply. `o_scan_done` means all row
commands have been accepted; the final row may still be drawing. A downstream
line controller must wait for that drawer too before declaring the line complete.

The caller must provide stable descriptor RAM during a scan. This block does not
copy RAM or select an original-board latch point. Static capture tests are not
evidence for the final policy with CPU writes active.

`run_sprite_scan_tests.py` checks 2049 synthetic line commands for each of two
lists: spread Y positions and all 63 sprites on the same Y. Counts 0/1/63,
priority boundaries, all 512 Y coordinates, unused upper RAM bits, skipped rows,
delayed replies, output stalls, changing upstream inputs and resets in all three
read phases/output/pre-request phases are checked. Each capture adds 216 visible
line commands and one directed line for reset testing. The reference report is
reference/sprite_scan_checks.json.

With `--draw`, the VHDL scan drives the actual VHDL/JTFRAME row engine. Every
selected row's sixteen pixels, positions, opacity and foreground tag are checked
against the direct ROM sampler. This mode waits for both scan and drawer to finish;
its normal-traffic tests complement the separate component reset tests. Results:
reference/sprite_scan_draw_checks.json. The crowded synthetic list takes at most
2816 clocks, or 58.67 microseconds at the 48 MHz evaluation clock. These figures
include independently delayed RAM/ROM responders and simulated consumer stalls;
they exclude line RAM clearing/writes, CPU traffic and shared SDRAM arbitration.
They do not establish a physical scanline deadline or final timing margin.

The selector alone also passes Quartus 17.0.2 synthesis/fitting at the 48 MHz
evaluation clock: commit 86e7df5, 100 ALMs, 80 registers and zero block RAM/DSP.
Worst setup slack is +10.535 ns and hold is +0.121 ns; every reported corner
and pulse-width check passes, with no illegal clocks or unconstrained paths.
See reference/sprite_scan_synth.json. This fit excludes the row drawer.

```powershell
./scripts/d_drive.ps1 scripts/run_sprite_scan_tests.py
./scripts/d_drive.ps1 scripts/run_sprite_scan_tests.py --draw
./scripts/d_drive.ps1 scripts/build_staged.py --synth-check sprite_scan
```

## Logical-line controller

`rabbitpunch_sprites.vhd` connects selection, JTFRAME row drawing, priority and
the two native line banks. It accepts a line command only while idle and after
any reset-induced RAM/ROM drains have completed. It latches bank, Y, count,
priority and flags, starts the clear and descriptor scan together, and holds
the first candidate until line storage is ready. Later descriptor lookup can
overlap drawing. The controller latches descriptor index at each row acceptance
so subsequent scan activity cannot change the priority of pixels already drawing.

Unlike the selector's `o_scan_done`, this controller's `o_line_done` waits for the
final row and RAM update pipeline to finish, making the completed bank readable.
The opposite valid bank can be read while this line is being built. This is
a logical-line interface; it does not synthesize physical sync/pixel clocks or
swap banks on a guessed raster event. Descriptor RAM must remain stable for
the requested scan; CPU-write scheduling/latching still needs integration.

`run_sprite_scan_tests.py --line` checks the connected primitives against every
native line entry in two synthetic cases and six captures. The `--renderer`
mode exercises the actual controller with continuous opposite-bank reads and
reset during descriptor fetch, first graphics fetch and second graphics fetch,
then verifies freshly cleared/re-rendered data. Both use the native RAM model,
independently delayed descriptor/graphics responders, reference descriptor-read
order and exactly two ROM reads per selected row. Renderer cycle measurements
include line clear and final update completion, and exclude test readback time.
These are not shared-SDRAM or physical scanline deadline tests.

```powershell
./scripts/d_drive.ps1 scripts/run_sprite_scan_tests.py --line
./scripts/d_drive.ps1 scripts/run_sprite_scan_tests.py --renderer
./scripts/d_drive.ps1 scripts/build_staged.py --synth-check sprite_renderer
```
