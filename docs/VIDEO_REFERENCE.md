# Video reference and bitmap RTL status

The complete images currently generated by scripts/render_reference.py come from
an offline Python model. They are not frames produced by VHDL or the MiSTer.
The model exists to establish expected pixels before implementing video hardware.

## Offline model checked against MAME

Six scenes are listed in scripts/mame/video_fixtures.json: each game's original
frame-1200 capture, plus coin/Start-scripted captures at frames 1000 and 1800.
Some scripted captures show course selection; a coin/Start action alone is not
proof that a screenshot is active gameplay. Every fixture is compared independently.

All six compare identically to the captured MAME screenshot: 62208 RGB pixels per
scene, 373248 pixels total. Reference source is pinned MAME 0.289 rpunch.cpp;
the generic packed-low-nibble-first tile layout and priority pixel operations
were also inspected in MAME's video/generic.cpp, drawgfx.cpp and drawgfxt.ipp.
Capture-region and output hashes are in reference/video_checks.json.

Reference comparisons use default MAME brightness/gamma with display shaders
disabled. Keep ROM audits tied to the pinned MAME 0.289 definitions. Reports of
analog brightness differences on other boards are not evidence for changing this
board's palette conversion; any such adjustment needs Rabbit Punch / Rabio Lepus
PCB evidence and a separate display-calibration check.
`scripts/check_reference_settings.py` recaptures both frame-1200 scenes with
explicit neutral options. Every RGB pixel and all ten dumped buffers remain
identical to the original references; see reference/neutral_settings_checks.json.

The model implements both 64x64 column-major tilemaps, tile ROM banks and palette
bits, 16x32 sprite decode/flip/clipping, sprite priority, bitmap overlay and RGB555.
The sprite X layout reverses each pair of packed bytes within a four-pixel group;
tile pixels use low nibble first. Bitmap pixels instead use high nibble first.

MAME's sprite draw walks high descriptor indices first and marks every opaque
sprite pixel as occupied in the priority bitmap, including pixels blocked by the
foreground. Later descriptors cannot overwrite an occupied sprite pixel. We copy
that behavior; the software renderer is not the FPGA's serial drawing schedule.

The captured Rabbit Punch GAME OVER text disappears when sprites are disabled,
together with the rabbit. That text uses sprites in this MAME scene. The bitmap
contains other elements such as STAGE: 1 and bottom status bars. The rabbit/text
overlap is present in MAME's own screenshot. This is not independent PCB evidence.

## Implemented VHDL bitmap reader

rtl/rabbitpunch_bitmap.vhd accepts a logical X/Y coordinate and video flags, then
requests one 16-bit bitmap RAM word through the memory backend's view port:

- source X = (input X + 4) modulo 512;
- word address = Y concatenated with source X bits 8..2;
- source X bits 1..0 select nibbles 15..12, 11..8, 7..4, 3..0;
- palette index = 512 + (flags bits 3..0 * 16) + pen;
- pen 15 is transparent.

It returns the coordinate tag, palette index and opacity. One request may be
outstanding, input metadata is latched on acceptance, and ready supplies explicit
backpressure. Reset discards the pixel and drains any accepted RAM reply before
accepting a new request. The backend must complete accepted requests across reset.
No composed-frame storage, pixel clock, raster, palette lookup or video output is
implemented by this block. Dynamic CPU-write collisions still need the measured
video scheduling policy; these tests use static captures after loading.

The synthetic RTL test checks all 512x256 coordinates, every palette bank and pen,
wrapping, byte/nibble order, changing inputs during a request, 0/3/11-clock reply
delays, and reset with a fetch outstanding. Six further tests load each 64 KiB bitmap
through the actual VHDL CPU memory request port and compare all 62208 visible pixels
through the actual VHDL view port. Results: reference/bitmap_checks.json.

Both tile layers now run through VHDL lookup adapters and JTFRAME row drawing;
see TILE_PIPELINE.md for captured pixel checks and preview provenance.
Sprite rows now run through a VHDL adapter and the same unchanged JTFRAME drawer;
see SPRITE_PIPELINE.md for captured row checks and the standalone fit. Sprite list
scheduling and drawing also pass connected static-data tests; see SPRITE_PIPELINE.md.
Sprite arbitration and palette-index mixing now match the six full MAME screenshots
with software-decoded layer stimulus; see VIDEO_PRIORITY.md for the scope.
Native sprite line RAM also passes directed and captured scan/draw integration
tests; the full logical-line controller also passes synthetic/captured lines,
global reset and concurrent display, plus its combined Quartus fit. Integrated
tile/bitmap/mixer/palette output, physical raster/PLL choices, complete-core
fit and hardware verification remain open. Six matching scenes do not cover every
register/flip/priority combination or establish a fully working game core.
