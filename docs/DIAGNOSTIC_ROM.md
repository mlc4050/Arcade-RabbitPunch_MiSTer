# Original ROM-free diagnostic

scripts/build_diagnostic_rom.py generates an original 68000 program, a silent Z80
loop and an inline development MRA under debug/diagnostic/full/. No game ROMs or
ZIPs are needed. The MRA is reassembled by the same loader-image tooling and must
match all 0x210000 generated bytes. unidasm independently disassembles the 68000
instructions. The first eight bytes are reset vectors, not executable opcodes.
No diagnostic artifact has been tested on the MiSTer or published as a release.

The program initializes bitmap palette pens 1..4 to red, green, blue and white,
disables sprites, fills every one of the bitmap's 32768 words with 0x1234, then
checks the CPU-visible ROM word at 0x020000 against 0xA55A. The intended completed
screen is repeating one-pixel red/green/blue/white stripes. Filling is visible as
it proceeds; wait for the completion signature before assessing the whole screen.
This tests the actual CPU program rather than overriding RGB at the framework.

After a successful check, word 0x0FC000 is 0xCAFE. The program repeatedly copies
player 1, player 2 and DIP reads into words 0x0FC002, 0x0FC004 and 0x0FC006, then
writes heartbeat 0xBEEF at 0x0FC008. Read-only main-request/write probes can show
that loop advancing. A ROM-word failure writes 0xDEAD at 0x0FC000 and changes the
white stripe's palette entry to red. No sound-chip exercise is included.

run_diagnostic_rom_tests.py executes the program on the unchanged fx68k with
delayed behavioral bus replies. The 64-word bounded test passes both normal and
corrupted-ROM branches, including exact sequential bitmap writes and input/DIP
copies. Both complete 32768-word cases also pass (reference/diagnostic_rom_full_checks.json). These tests validate instruction encoding/control flow and bus accesses,
not the native RAM/controller, visible RGB, full SDRAM capacity or hardware pins.
The full RGB image remains unverified until a native-renderer or board capture.

Generate with scripts/d_drive.ps1 scripts/build_diagnostic_rom.py. The shorter
--test-short image is for simulation and is kept in a separate directory; do not
substitute it for the full hardware-fill image. No source has been installed or
launched on the device. Normal game MRAs remain unchanged.


The native integration test is scripts/run_diagnostic_video_tests.py, using
sim/board/diagnostic_video_tb.vhd. It retains the real PLL/fractional enables,
shifted SDRAM chip model, native board RAM and continuous shared graphics path.
The intended checks are every executed bitmap write, normal/corrupt ROM branch,
one complete 288x216 RGB frame, no underflow, the 3024-clock row budget, and the
completion signature through the paused native RAM inspection port. These checks
are currently running; no completed native RGB result is claimed yet.

The default run directly preloads the ROM fixture and performs a real 32-byte
header download. --full-download instead sends the whole original 0x210000-byte
image through the native word interface without a memory deposit. Neither mode
exercises the ARM HPS frontend or physical pins. --corrupt changes the checked
ROM word and expects the white stripe to become red. Separate output directories
keep normal, corrupt and full-download cases independent.

The first native run was deliberately stopped after measuring progress: 462
bitmap words by 2.057 ms simulation time made the initial one-hour wall budget
insufficient for the full fill and frame capture. Its source and partial transcript
are retained in reference/diagnostic_video_initial_progress_measurement.json;
this is an incomplete measurement, not an HDL assertion failure or a timed-out
pass. Unchanged checks are being rerun with --wall-timeout 18000.
